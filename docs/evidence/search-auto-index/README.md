# 搜索自动使用索引 · 性能测量

2026-11-06。比较同一棵真实文件树上“默认搜索自动规划（索引可用时用索引，宽匹配回退实时扫描）”与“未覆盖位置实时扫描”的搜索 Worker 延迟。原始数据：[search-latency-20k.json](search-latency-20k.json)。

## 方法

- 20,000 个真实文件，200 个目录：50% `报告_XXXXXX.txt`、30% `数据_XXXXXX.csv`、20% `note-XXXXXX.md`，另有一个 `needle-unique-report.txt`。
- 同一进程内建持久索引（`file-index.sqlite`，WAL）后测量：
  - `auto`：默认 `FileView`（`indexed=false`）在已索引根内搜索，走本轮新加的规划器/选择性保护；
  - `live`：同一查询从“有有效空索引、但根未覆盖”的位置执行，保持实时扫描（等价于改动前的默认路径）。
- 每个场景 3 次冷查询（每次新建 Worker，先跑一次无关查询让线程就绪并占 1 条缓存，被测查询仍是该查询的缓存未命中）+ 2 次暖查询（同一 Worker 的缓存命中）；页面请求为 0..32（与生产首屏一致），使用 release 构建。
- 计时从 `Worker::search_view` 到收到 `done` 进度事件；`first_page` 为收到首个 `Page` 事件。结果为桌面 x64 单机、OS 文件缓存已热（文件刚创建）的样本，不是跨硬件或 GPU/输入到像素延迟结论。

## 结果（冷查询，中位数；暖值为两次样本）

| 场景 / 查询 | 命中数 | 规划器选择 | auto 完成 ms | live 完成 ms | 完成加速 | auto 首屏 ms | live 首屏 ms | auto 暖 ms | live 暖 ms |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 精确文件名 `needle-unique` | 1 | 索引 | 64.9 | 227.1 | **3.50×** | 60.3 | 14.1 | 36.0 | 11.6 |
| 前缀 `note-000` | 200 | 索引 | 114.0 | 227.2 | **1.99×** | 100.1 | 16.7 | 44.8 | 14.8 |
| 中文单字 `报` | 10,000 | 回退实时扫描 | 522.3 | 530.4 | 1.02× | 47.5 | 16.8 | 31.2 | 19.4 |
| 宽 ASCII `note` | 4,000 | 回退实时扫描 | 348.4 | 322.6 | 0.93× | 37.8 | 19.7 | 35.3 | 24.9 |

索引构建：24,621.7 ms；索引库 28,626,944 B（约 27.3 MiB）。

## 解读

- 对“找具体文件/窄前缀”的搜索，在 2 万文件树上完成时间从约 227 ms 降到 65–114 ms（2–3.5 倍）；索引候选越少收益越大。
- 宽匹配（中文单字、常见 ASCII 词）在旧的“每个候选都核对当前身份”实现下反而更慢，因此本轮加入了选择性保护：先用 `scope_size` 和 `estimate_matches` 估算命中量，预计候选过多时直接回退实时扫描。表中宽匹配的 auto 列就是回退结果，只有约 1% 的规划开销（ASCII 宽查询的 0.93× 在噪声与规划开销范围内），没有把慢路径暴露给用户。
- 两个仍待优化的成本已记录为后续项：
  - 暖查询的索引路径要重新做 open/规划/水位/选择性预检，耗时约 31–45 ms，而实时扫描的暖缓存命中约 10–25 ms；可在缓存命中时跳过选择性预检（缓存条目本来就来自受保护的查询）。
  - 精确/中等的索引查询首屏晚于实时扫描：实时扫描边扫边产出首批页面，而索引路径要等规划、预检和首批候选后才发页；需要把首屏发页提前或缓存规划结果。
- 索引构建本身（2 万文件约 24.6 s）说明步骤 ② 的空闲调度/限速必要，本轮未改变构建调度。

## 选择性阈值敏感性（同一棵树，20,201 个索引项）

对 `/24` 阈值做 8 / 24 / 64 三档扫描（`scope_size=20,201`，对应上限 2,525 / 841 / 315 个候选；2 次冷查询，live 基线只测一次）。数字为“auto 完成中位数相对 live 的加速”，括号内是规划器是否选择索引。原始数据：[match-budget-sweep-20k.json](match-budget-sweep-20k.json)。

| 命中数 | /8（上限 2,525） | /24（上限 841） | /64（上限 315） |
| ---: | --- | --- | --- |
| 1 | 3.57×（索引） | 3.89×（索引） | 3.87×（索引） |
| 200 | 1.82×（索引） | 1.62×（索引） | 1.72×（索引） |
| 500 | 1.10×（索引） | 0.91×（索引） | 0.86×（回退） |
| 2,000 | **0.43×（索引，慢 2.3 倍）** | 0.90×（回退） | 1.19×（回退） |
| 4,000 | 0.89×（回退） | 0.98×（回退） | 0.99×（回退） |
| 10,000 | 0.94×（回退） | 0.89×（回退） | 0.93×（回退） |

（回退行的加速约为 1，1.19× 与 0.86× 是 live 基线只测一次带来的跨轮噪声；绝对值见原始 JSON。）

用这些点拟合本机单位成本：实时扫描约 11.4 µs/索引项（约 230 ms / 20,201 项）；索引路径约 63 ms 固定开销 + 0.36 ms/候选（1→62.8、200→136.8、500→242.9 ms 三点近似线性）。因此交叉点约 `(221−63)/0.36 ≈ 440` 个命中，即“子树项数 / 46”。结论：

- `/8` 会把索引选择范围放到 2,525，远超交叉点；2,000 命中时实测 747 ms 对 live 319 ms，明确回退（真实回归），不可接受。
- `/64` 低于交叉点，不会回归，但会放弃“命中数在 scope/64 与 scope/46 之间”的索引收益；该带宽随树规模线性增大，大树上的损失会更明显。
- `/24` 略偏激进：上限 841 超过交叉点约 1.9 倍，实测 500 命中时 243 ms 对 221 ms（0.91×），处在边际。
- 依据这批数据，更接近交叉点的系数是 `/46`–`/48`；当前代码默认仍是 `/24`，是否调整为 `/48`（并复核小文件夹与 10 万项大树）留待确认。
- 96 下限和 4,096 上限本轮未被触发（20k 树三档上限都未到 4,096）；下限用于让小文件夹的窄查询仍走索引，上限把最坏情况身份核对时间限制在约 1.5 s（4,096×0.36 ms），两者都还缺小树/大树实测数据。

## 按父目录批量身份核验（本轮）

搜索候选与可见页的身份核验改为按父目录分组：同一父目录 ≥8 个候选时，用一次 `DirectoryReader` 批量枚举替代逐文件 `CreateFile`；不足 8 个或批量枚举不可用时回退逐文件 `identity::capture`。原“每个候选仍核对身份”的正确性语义不变。原始数据：[search-bulk-validation-20k.json](search-bulk-validation-20k.json)。

同一 20,000 文件/200 目录树，新增一个“同一目录 60 个 `local-*.txt` 命中”的场景；基准通过测试专用开关对同一查询做 A/B（生产固定走批量路径）：

| 指标 | 无批量核验 | 批量核验 | 加速 |
| --- | ---: | ---: | ---: |
| 首屏中位数 | 33.4 ms | **18.8 ms** | **1.78×** |
| 完成中位数 | 37.8 ms | **18.8 ms** | **2.01×** |

同一场景 auto（索引）对 live（实时扫描）：首屏 16.0 ms 对 27.2 ms（1.70×），完成 20.6 ms 对 27.2 ms（1.32×）。批量核验的收益集中在“同一目录多命中”的文件夹内搜索；跨目录的全局搜索每组候选少，仍走逐文件回退，不增加额外目录枚举。

## 短查询 2-gram 扩展与预检缓存（本轮）

`grams` 从“CJK 单字/双字”扩展为“任意相邻 2 字符对 + CJK 单字”。新增库直接写入完整集合；旧库由 writer 启动时一次性回填并写入 `meta('grams_v2')`，读端在回填完成前仍用旧规则（CJK grams / `instr`），不会读到不完整结果。代价与收益（同一 20k 树）：

- 维护代价：构建 13.2 s → **16.8 s**，索引库 29.5 MB → **40.6 MB**；逐条增量 3.0→4.3 ms，批事务 2.6→3.2 ms；无变化重扫维持 1.1 s。
- 查询收益（2 字符 `ue`，1 命中，同窗口 A/B）：

| 路径 | 首屏中位数 | 完成中位数 |
| --- | ---: | ---: |
| 扩展 2-gram | **59.2 ms** | **66.9 ms** |
| 旧 `instr` 回退 | 129.5 ms | 186.2 ms |
| 加速 | **2.19×** | **2.78×** |

- 同一查询相对实时扫描：完成 64.1 ms 对 236.0 ms（3.68×）。
- 1 个非 CJK 字符（`q`）仍走 `instr`：索引完成 186.3 ms 对实时扫描 206.0 ms（1.10×），首屏仍晚于实时扫描，未强行宣称收益。
- 同目录 60 命中的 2 字符查询 `lo`（重新扫描 400 项的小目录）：索引 18.1 ms 对实时扫描 17.5 ms，小目录实时扫描已足够快，索引路径没有回归但也无收益。

预检缓存：结果缓存命中且索引 revision/水位未变（`Cache::contains` + `Stamp::follows`）时跳过 `estimate_matches` 选择性预检；缓存未命中或索引已变化时仍执行原预检。原始数据：[search-short-grams-20k.json](search-short-grams-20k.json)。

## 复现

```powershell
./scripts/native/search-benchmark.ps1 -Files 20000 -Dirs 200 -ColdRuns 3 -WarmRuns 2
# 阈值扫描（同一 worker 成本模型，divisor 8/24/64）：
cargo test --release --locked -p backleaf match_budget_threshold_sweep_real_files -- --ignored --nocapture
```

环境：Windows 11 家庭版 26200，AMD Ryzen 7 8745H（8C/16T），19.8 GiB 内存；rustc/cargo 1.99.1；源码 `4e1d10e` 加本轮未提交改动；`--release`。

限制：Worker 级延迟，无 UI 帧、GPU、输入到像素或冷磁盘结论；单机单次样本，绝对值随 NTFS/杀毒/磁盘状态变化；`first_page` 受 Worker 页面请求时序影响（索引查询可能在首个候选批次前就完成全部工作），不作为最终产品时延承诺。
