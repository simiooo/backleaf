# 大规模文件处理 · v5.1

本轮将“超多文件”同时作为 UI 和资源预算约束。工程初始验证规模为 1 万、10 万、100 万条目，24 个逻辑任务，并包含极长 UTF-16 路径、大量失败和多个窗口。这些规模及以下数字是本轮工程选择，未经过产品或实机性能验收。

## 用户看到的行为

- 标题栏只保留一个任务入口，显示任务数；没有给每个文件新增窗口、卡片或通知。
- 汇总面板高不超过 360 px，最多显示四个任务，其他任务在同一列表中滚动查看。详细结果切换到同一入口下的面板，高不超过 380 px，不无限增加页面高度。
- 详情右上角“×”仅收起面板，任务继续；终止批次必须点明确的“取消”。准备剪贴板也保留标题栏入口，收起进度后仍可返回。
- 一个任务可以包含十万或百万文件。默认看总量、已完成数、当前文件；需要时查看“全部 / 处理中 / 失败”，搜索该批次的文件。滚动明细时保持位置，不被新进度抢走；定位当前文件是主动动作。
- 大量失败先给完成/未完成数量和原因统计，按需查看具体文件。只重试未完成项；同名决策仅作用于该任务中明确的冲突范围。不会弹一万个错误对话框，也不会重做九万个成功项。
- 排队显示原因：设备忙、路径冲突、等待用户决定或位置不可用。独立任务可以继续；正在等待的任务不能伪装成正在传输。
- 准备期间显示“已发现/已准备多少项”，总量未知时没有假百分比。准备剪贴板可取消；只有系统剪贴板成功接收后才进入已复制/已剪切状态，失败时不破坏已有剪贴板。
- 取消先显示“正在取消”，停止新工作并等待当前系统操作真实终止。成功、跳过、失败、取消及尚未核对的结果分开记录；不假装回滚已完成文件。当前不提供未经验证的暂停/恢复按钮。
- 文件网格仍然居中，保持 88 px 单元、12 px 行距。行内重命名错误使用锚定提示，不改变整个大目录的行高或滚动位置。

设计页 31–38 分别覆盖百万目录选择、24 任务汇总、十万文件明细、一万失败结果、大批次取消、窄窗队列、百万选择准备和性能契约。稿中仅创建可见区域的样例图层，数量是设计数据，不代表已生成百万文件或已实现虚拟化。

## 渲染、数据与选择

GPUI 采用固定行高的虚拟列表承载网格行，而不是创建全部文件的元素树。每行按当前列数取文件；只实现视口与少量预取。上游 [uniform_list 源码](https://github.com/zed-industries/zed/blob/d36a70661471ec64dce230798121d554930d5c60/crates/gpui/src/elements/uniform_list.rs) 提供可见范围回调；实际网格、焦点、命中与 UIA 必须在 SIM-935 验证。

目录、任务队列和失败明细都采用稳定身份及游标分页。显示页只取 ID、显示文件名、简短状态和图标键；完整路径与扩展属性在执行动作或用户查看时加载。不在滚动路径解码几十条超长路径，不用每帧深 OFFSET 查询。排序与文件发现放在后台；按版本与可见锚点一次提交结果，保持焦点和选择稳定。

Ctrl+A 表示“该目录快照全部项减去排除项”，而非在每个窗口复制百万个 ID。操作提交时将确定的选择逐批固化为磁盘清单，避免新出现的文件被悄悄加入删除/移动。读取中的目录必须区分已发现条目与完整快照，不能暗示尚未发现的文件已经被操作。身份、重命名、外部变更与再次执行前的验证仍由系统适配层负责。

缩略图和系统图标按可见区域低优先级加载，使用按实际字节计费的 LRU；默认缓存预算 64 MiB、同时解码 2 项。离屏/旧窗口代次请求取消或丢弃。跨窗口共享有界缓存，不能按文件总数永久缓存图像。大批量变更合并刷新受影响条目，目录监视溢出时后台核对，不每个回调全量重扫。

## 有界后台流水线

| 资源 | 初始策略 |
| --- | --- |
| 应用自有数据批次 | 最多 256 条、256 KiB 编码负载或等待 50 ms，先达到哪个先提交 |
| 待处理数据队列 | 8 个批次；路径长度也计费，不能只限制条数 |
| 文件操作执行 | 全局最多 2 个；默认每个物理设备/网络目标 1 个，无法识别时保守串行 |
| 设备预约 | 同时预约源和目标，统一排序并原子授予；避免互相等待死锁 |
| 公平性 | 独立任务在批次边界轮转；需用户决定或离线时释放可释放的设备额度 |
| 结果存储 | SQLite 磁盘清单和逐项结果；事务批量写入，内存只保留有界批次和摘要 |
| 界面进度 | 可见时最多 10 次/秒；隐藏时最多 1 次/秒；一个待处理唤醒合并最新进度 |
| 取消和安全控制 | 独立控制信号，不排在文件数据队列之后；最终结果及时刷新 |
| 可访问进度 | 最多每 2 秒播报进展；用户动作、阶段变化和失败单独反馈 |

以上是应用自有资源预算，不是 Shell 内部递归、OLE、驱动或扩展占用的保证。原生对象必须在各自 STA 使用；不能为了并行把未封送的 COM 对象传到工作线程，也不能无限增加线程。设备并发策略须用 SSD/HDD/USB/SMB 的实际竞争场景再调优。

化妆性进度可以合并；终态、错误和取消结果不能丢失。慢消费者对后台施加背压，UI 主线程不等待文件 I/O 或 SQLite 写入。结果入库失败时停止派发并标为待核对，不用一条成功提示掩盖丢失的结果。

逐项终态“不丢”指完整保留结果记录，不代表每个文件结束都重绘。文件级结果可合成一个最新数量快照；任务级结束、取消和需要用户处理的状态及时唤醒，并仍共享单个待处理唤醒。50 ms 定时提交和隐藏窗口 1 Hz 是应用集成目标，当前隔离模型只验证条数/字节限制与可见状态的合并策略。

Windows Shell 仍负责复制、移动和回收语义。`CopyItems` 只声明工作，`PerformOperations` 才执行；不能把百万 `IShellItem` 一次积存在一个长生命周期操作对象里。顶层选择按受控批次提交，但一个目录内部的递归由 Shell 处理，其峰值内存另测。不能为省内存自行展开递归回收而破坏原目录恢复语义，也不能假定分批工作具有统一撤销或原子回滚。

同对象、父子路径、重解析别名、硬链接和同名目标需要身份及访问冲突协调，未知关系保守串行。文件系统与结果数据库之间没有跨系统原子事务；崩溃后仅核对未确定项，不自动重放破坏性操作。定制冲突 UI 与 Shell flags 的接入是 SIM-935 验证项，不得为压测静默覆盖或把无法回收改为永久删除。

## 两项需要明确的原生边界

Windows [UpdateProgress](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperationprogresssink-updateprogress) 返回的是工作量估计点，没有字节单位。v4 的示例 MB 进度已删除：有真实字节回调时才展示字节、速度和可靠的时间估计；否则显示阶段、实际完成数和工作量指示。未知总数先用活动状态，不能把“已发现”当作最终总量，不能把不同度量的任务百分比简单平均。结束时同时核对逐项结果和 [GetAnyOperationsAborted](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-getanyoperationsaborted)。

系统 [CF_HDROP](https://learn.microsoft.com/en-us/windows/win32/shell/clipboard#cf_hdrop) 包含完整路径数组，最终内存会随路径总长度增长。应用内部的分页选择不能消除这个系统格式成本。OLE 准备放到不阻塞 GPUI 的受控流程，预估 UTF-16 负载并单独计量；初始临时负载预算 256 MiB，超出或系统分配失败时明确报告“无法准备剪贴板，请减少选择后重试”，保留原剪贴板。不悄悄退化为只在本应用可粘贴的私有格式。外部互操作、延迟渲染、所有权存续及异常退出必须在真实 Explorer 上验证。

## 验证与进入产品的条件

| 指标 | 初始验收目标 / 测法 |
| --- | --- |
| 滚动 | 目标 60 Hz，帧时间 P95 ≤16.7 ms；在实际 GPU、DPI 和开明细情况下测量 |
| 键盘、选择、取消反馈 | P95 ≤100 ms；记录输入至绘制，取消反馈与系统停止延迟分开 |
| 首屏 | 本地暖缓存首次可见项目标 ≤500 ms；冷盘、网络和完整排序分开报告 |
| 常规条目增量内存 | 从 10 万到 100 万不随条目线性增大；普通路径记录层初始目标 ≤128 MiB，不含图像缓存、Shell/OLE 独立预算 |
| 结果正确性 | 每项恰好一个可核对终态，错误不漏、取消不新派发、失败重试不重做成功项 |
| 特殊情况 | 长 UTF-16 路径、目录树、盘符/设备别名、空间不足、目标断开、同名、拒绝访问、监视溢出与异常退出 |

当前隔离验证位于 [probe.py](../spikes/bulk-scale/probe.py)，结果为 [bulk-scale-model.json](evidence/bulk-scale-model.json)。它验证 SQLite 磁盘记录、有界负载、可见页、合并进度以及满队列下的取消控制。它不调用 Shell、不复制真实文件、不测 GPUI 帧率。完整限制随报告列出。

本机 Windows 11 / Python 3.12.10 / SQLite 3.49.1，单次模型样本：

| 数据规模 | 进程峰值工作集 | 96 条可见页暖读 P95 | 保留终态 |
| --- | ---: | ---: | ---: |
| 100,000 | 35.65 MiB | 0.160 ms | 100,000 |
| 1,000,000 | 39.82 MiB | 0.201 ms | 1,000,000 |
| 1,024 条约 32K 字符路径 | 33.17 MiB | 0.140 ms | 1,024 |

普通路径队列实际峰值编码负载 233,472 字节；极长路径实际峰值 2,045,248 字节，均在 8 × 256 KiB 上限内。极长路径批次自动降为 4 条，说明只限制条数是不够的。百万条目中 10,309 项模拟失败均保留；1,000,000 次化妆性进度更新被合为 251 次快照，最多一个待处理唤醒。这里只证明该模型，不能据此声称应用只占 40 MiB。

另做 [同库长路径对照](evidence/long-path-page-comparison.json)：同一数据库、相同页大小，读取并解码完整路径的 P95 为 22.832 ms，读取短显示字段为 0.171 ms。完整路径单条按需读取的 P95 为 0.464 ms。它是本机暖读样本，不是跨设备保证。

覆盖索引有磁盘与写入成本：当前百万记录模型数据库为 183.85 MiB，早期非覆盖索引模型为 100.10 MiB。两个不同版本的落盘耗时不作严格 A/B 结论；后续 Rust schema 应在分离路径数据、覆盖索引、写放大与实际查询模式之间选择。不能只展示读延迟而隐藏额外存储成本。

基线发现：把 96 条完整超长路径带入可见页，会花时间读取及解码数 MiB 的路径。当前模型改为覆盖索引读取短显示字段，完整路径单条按需取出；前后数据分别保留在 `evidence`。冷枚举、排序、真实设备吞吐和各系统预算仍未验证，不能凭模型报告宣布性能交付完成。
